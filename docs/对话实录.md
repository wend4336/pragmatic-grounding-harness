# 对话实录

> 整理范围：从文章阅读请求到 Agent Runtime 与 DSH Meta-Host 的架构讨论。仅整理实质性对话，不包含检索、核对和仓库发布等操作过程。

## 第一轮：Pragmatic Grounding 与五种 Harness

### 用户

阅读 [《Harness 到底是怎么回事？》](https://mp.weixin.qq.com/s/s7WgQnhuYWUkFBbPu_QaGQ)，理解这篇文章的核心观点 Pragmatic Grounding。从“Harness 是 LLM 的 Host，而 Agent 是 LLM 的 Purposes 在 Harness 环境中 Runtime”这一核心原则出发，分析 DSH、Claude Code、Codex、Pi dev 和 Work Buddy 五个 Harness 在理解和实现 Pragmatic Grounding 工程路线上的差异。

### 助手

我的核心判断是：这五条路线的差异，不在于谁接的工具更多，而在于它们如何回答三个问题——Purpose 在哪里被实例化，什么环境反馈被视为“真值”，以及行动经验最终沉淀到哪一层。

简言之：

- **DSH**：让承载接地的 Host 本身变成可组合、可替换的运行时对象。
- **Claude Code**：把接地做成可编程、可分工的人机协同行动循环。
- **Codex**：把接地做成有明确执行边界、可隔离委派和审查的任务循环。
- **Pi dev**：尽量缩减预设 Host，把构造接地环境的权力交给用户和模型。
- **WorkBuddy**：把接地从代码仓库推进到企业业务系统、组织角色和持续工作流程。

#### 1. Pragmatic Grounding 的两个闭环

文章并不是说“模型调用工具，所以理解了世界”。其完整逻辑是：

```text
运行时接地闭环：

Purpose
  → LLM 生成符号与行动
  → Harness 将行动作用于环境
  → 环境状态发生变化
  → 观察、报错、测试结果返回模型
  → 模型修正下一步行动
```

这使模型生成的符号不再只是“关于行动的描述”，而成为真实状态转移的一部分。

在此之上，还有第二个闭环：

```text
学习／内化闭环：

经验证的交互轨迹
  → 清洗、结果验证、因果归因
  → 后训练或轨迹微调
  → 新模型形成更强的行动先验
  → 减少对外部流程提示的依赖
```

这里必须严格区分三种“经验沉淀”：

1. 写进上下文、记忆或知识库：下次可以被读取；
2. 沉淀为 Skill、Hook、插件或工作流：下次可以被调用；
3. 进入模型权重：变成不依赖显式外部提示的原生策略。

前两种是外化经验的保存与复用，只有第三种才是文章严格意义上的 Harness Internalization。不能看到一个产品支持记忆、Skill 或插件，就说它完成了权重内化。

文章最后还保留了一条更重要的边界：策略内化不等于后果经验内化。模型可以学会“如何把事情办成”，却并不因此亲自承担资金损失、数据破坏或社会关系受损。

#### 2. 从 Host—Purpose—Runtime 重新划定三层

按照用户给出的原则，可以写成：

```text
Agentₚ = RunH(LLM, Purpose, State)
```

其中：

- LLM：提供生成、推理和行动选择的策略先验；
- Harness／Host H：提供上下文、工具、执行介质、状态、权限、调度、观察和验证机制；
- Purpose：用户或组织托付的目标、角色、约束与验收标准；
- Agent：Purpose 在 Host 中被实例化后的、带有持续状态和行动轨迹的运行过程。

这里的 Purposes 最好理解为用户和组织的目的，而不是 LLM 自发拥有的欲望。

因此：

- Agent 不是一段 persona Prompt；
- Subagent 不是另一个模型，而是另一个具有独立目的和上下文的运行实例；
- 同一个 Agent 可以更换底层模型，而保持目的与任务身份不变；
- 同一个模型也可以在 Host 中同时支撑多个不同 Purpose 的 Agent。

评价一个 Harness 的语用接地能力，可以用一个概念公式：

> 有效接地 = 目的绑定 × 行动有效 × 观察保真 × 验证独立 × 状态连续 × 后果治理

它是乘法而不是加法：工具再多，如果没有独立验证，仍可能只是流畅地自我确认；权限再大，如果没有目的绑定，也只会扩大错误行动的影响范围。

#### 3. 五种工程路线总览

下表描述的是架构重心，不是功能有无的绝对边界。

| Harness | Host 的主要形态 | Purpose 的主要实例 | 主要“真值”来源 | 经验首先沉淀到 |
| --- | --- | --- | --- | --- |
| DSH | 可分层组合的插件树 | 配置化运行环境中的任务过程 | 工作区、工具、命令、沙箱及其返回 | 插件、Profile、配置与运行轨迹 |
| Claude Code | 有明确产品意见的编码引擎和生命周期 | 主会话、子代理及协同任务 | 代码库、测试、diff、Hook、人的即时纠偏 | CLAUDE.md、记忆、Skills、Hooks |
| Codex | 本地／云端受约束的任务执行环境 | 被委派的编码任务 | 沙箱内执行结果、测试、变更与审查 | AGENTS.md、Skills、插件和环境配置 |
| Pi dev | 极简 Agent Loop、TUI 与 SDK | 用户自行组装的工作流 | 文件、Shell 及所安装扩展的反馈 | Extension、Skill、Prompt、Package |
| WorkBuddy | 企业工作台与托管 Agent 运行时 | Expert、Assistant、Team、企业自定义 Agent | 业务文件、企业系统回执、交付物与组织评价 | Skills、知识库、专家模板、轨迹与评估 |

#### 4. DSH：让环境本身成为可计算对象

DSH 的关键不是“插件多”，而是模型适配器、工具注册表、会话日志乃至 Agent Loop 本身都是可替换插件；一个运行实例则由 Profile、Bundle 和 Patch 等层次组合成插件树。

用 Host—Purpose 的语言说：DSH 不只让 Purpose 在 Host 中运行，还让 Host 的组成方式能够随目的而重构。

这带来一次抽象层级跃迁：

- 普通工具型 Harness：Purpose 决定“调用哪个工具”；
- 工作流型 Harness：Purpose 决定“走哪条流程”；
- DSH 路线：Purpose 所依赖的模型、Loop、存储、沙箱和工具组合，都可以成为被重新组织的对象。

所以，DSH 对 Pragmatic Grounding 的独特贡献是 Host 的可塑性与可替换性。

但要注意：可组合性不等于接地真实性。换掉 Agent Loop，并不保证行动更正确；增加插件，也不保证反馈更真实。DSH 仍需要独立验收器、权限边界、轨迹归因和结果回放，否则“Harness of Harness”也可能只是更复杂地生成自我确认。

同时，文章只确认这种架构具有积累、回放语用轨迹的潜力，并没有断言 DSH 数据已被系统性用于下一代 DeepSeek 模型的后训练。

#### 5. Claude Code：可编程的协同行动循环

Claude Code 以代码库读取、文件编辑和命令执行为基本闭环，并通过 CLAUDE.md、自动记忆、Skills 与 Hooks，把项目规范、跨会话经验和重复工作流程接入运行时。

它最有代表性的不是某个单独工具，而是生命周期可编程性：

- Hook 可以插入会话、回合和工具调用等生命周期节点；
- PreToolUse 可以在行动发生前阻止调用；
- 行动后的检查可以再把结果反馈给模型；
- 子代理拥有独立上下文、系统提示、工具访问和权限，使 Purpose 能被拆成多个边界明确的运行实例。

因此，Claude Code 的路线可以概括为：在模型与环境的每一次接触周围，布置可编程的观察、约束、验证和分工机制。

人的位置也不只是最后审查者，而可以持续存在于行动循环中：即时纠偏、定义项目规范、设置前置门槛、决定何时停止。

它经验内化的主要工程载体是记忆、Skills、Hooks 和子代理配置。这些机制能让未来运行更少依赖重复提示，但仍属于外部行为结构的保存与重组，不能直接等同于权重更新。

#### 6. Codex：有硬边界的任务执行与结果审查

Codex 的架构重心是：先规定 Agent 可以自主行动的技术边界，再让 Purpose 在边界内持续运行。

其本地沙箱约束命令可以修改哪些文件、能否访问网络；任务需要越界时，则由审批流程接管。沙箱与审批不是同一个东西：前者限制实际能力，后者决定何时必须询问。

在云端，每个任务拥有独立工作区；AGENTS.md 则把全局和项目级规范组成分层指令链，使任务目的进一步接地到具体仓库的工程约定。

与 Claude Code 相比，可以这样理解二者的重心：

- Claude Code 更强调行动循环的可编程协同：在生命周期中插入策略、验证和角色分工；
- Codex 更强调执行边界与任务隔离：让任务在受约束环境中自主推进，再把监督集中在边界与结果上。

这不是说彼此没有对方的功能，而是两种治理思路：一种偏向管理行动过程，另一种偏向管理行动范围与交付结果。

Codex 的边界也有明确的认识论限制：沙箱能证明行动发生在哪里，测试能证明某些程序性质成立，但二者都不能证明最初的目的值得做，也不能证明代码变更一定产生产品价值。

#### 7. Pi dev：通过减法让 Host 自己长出来

Pi 的官方定位是极简、可扩展的 Agent Harness。它减少预设工作流，鼓励通过扩展、Skills、Prompt 模板和 Package 构造自己的工作流。

它代表的不是“弱版 DSH”，而是另一种设计哲学：

- DSH：把 Host 的每个组成都变成可替换对象；
- Pi：先尽量移除预设，只保留最小核心，让使用者决定 Host 应该长什么样。

所以 Pi 的接地路线是：不预先替 Purpose 规定过多行动结构，而让 Purpose 与真实环境碰撞后，再把有效结构写成扩展。

这使“构造 Harness”本身成为任务的一部分。成功经验可以转化为代码、扩展或技能，而不是只留在一次会话里。

但极简并不自动等于更好的接地。Pi 把最大的自由也连同最大的责任交给了使用者：验证器要自己选，权限边界要自己建，哪些经验值得固化也要自己判断。

#### 8. WorkBuddy：从“代码是否通过”转向“组织工作是否完成”

WorkBuddy 将 Experts、Skills、知识库、多平台连接、定时任务和业务交付物放入同一个企业工作环境。

用 Host—Purpose 框架映射：

- Expert：更接近可复用的 Purpose 模板，而不只是一个角色 Prompt；
- Assistant／Team：是这些目的被持续运行、协同执行后的 Agent 形态；
- Managed Agents：进一步把身份、运行环境、连接、追踪和评估变成托管 Host 的基础设施。

这意味着接地点发生了变化：

```text
Coding Harness：
代码修改 → 编译／测试 → diff／PR

Work Harness：
业务目标 → 文件与企业系统操作 → 交付物／系统回执
          → 人、团队和业务结果的验收
```

但这里也遇到了最困难的验证问题：

> “生成了一份可打开的报告”不等于“报告结论正确”；“成功发送了一封邮件”不等于“实现了沟通目的”；“更新了工单”不等于“做出了正确的业务判断”。

因此，WorkBuddy 路线最需要的不是更多 Experts，而是业务语义级 Eval、独立验收、权限分级、审计与责任归属。它更现实的经验内化方向是组织知识、Skill、专家模板、Agent 版本和评估体系的持续迭代。

#### 9. 结论

这五者不适合排成“低级到高级”的单线序列：

- DSH：Host 的接地，行动环境本身可以被组织、替换和重构；
- Pi：Host 构造权的接地，用户和模型可以把实际目的转化为自己的运行结构；
- Claude Code：行动过程的接地，通过生命周期、Hooks、子代理和人的持续介入校正行动；
- Codex：任务执行的接地，通过沙箱、独立工作区和结果审查赋予自主行动明确边界；
- WorkBuddy：组织目的的接地，让 Agent 进入真实业务对象、企业系统和持续性组织流程。

一句话收束：

> DSH 让 Host 可计算，Pi 让 Host 可自建，Claude Code 让行动循环可编程，Codex 让任务执行可界定，WorkBuddy 让 Purpose 进入组织。

越接近真实业务世界，Pragmatic Grounding 就越不只是一个“让模型更能干活”的能力问题。它会同时成为一个 Exposure Governance 问题——谁授权、谁验收、谁能够回滚，以及当行动造成不可逆后果时，究竟由谁承担。

## 第二轮：公式的重要性与 DSH 编排其他 Harness

### 用户

`Agentₚ = RunH(LLM, Purpose, State)` 这个公式总结得很成功，它比 DSH 自己提出的 `Agent = Model + Harness` 更准确。这也解释了 DSH 能让承载接地的 Host 本身变成可组合、可替换的运行时对象，而其他四个 Harness Agent 都可以成为 DSH 的插件，被 DSH 调用。AI 的行动力，比 LLM 生成的 Purposes 更重要，这就是这个公式的重要性。

### 助手

这个推进很关键，不过需要保留一个边界：“可以被 DSH 编排”不等于“整个 Harness 被压平成一个 Agent 插件”。更准确的结构应当是嵌套 Host——这样才能把 DSH 的调度权、子 Harness 的环境权，以及具体 Agent 的 Purpose 分开。

这个公式真正改进的地方，是把 `Agent = Model + Harness` 里的静态加号换成了动态的 `Run`：Agent 不是模型与工具的静态拼装，而是一个由 Purpose 驱动、由 Host 承载、由 State 保持连续性的运行过程。

不过，有两个地方需要进一步拧紧。

#### 1. 其他 Harness 接入 DSH，应当是嵌套 Host

从工程集成上，其他 Harness 可以通过 CLI、SDK 或 API 被外部系统调用；但“可以被 DSH 编排”不等于“DSH 官方已经提供现成插件”，也不等于整个 Harness 在概念上退化成一个 Agent。

更准确的关系是：

```text
DSH：Meta-Host／Host of Hosts
  │
  ├── 插件适配器：启动、观察、打断、恢复、收集结果
  │
  └── 子 Harness：Claude Code／Codex／Pi／WorkBuddy
          │
          └── Agentₚᵢ：具体 Purpose 的运行实例
```

公式可以展开为：

```text
Agentₚ = RunDSH(LLM₀, Purpose, State₀)
              │
              └── Delegate(Purposeᵢ)
                    → RunHᵢ(LLMᵢ, Purposeᵢ, Stateᵢ)
```

这里要区分三个对象：

1. DSH 插件：只是调用子 Harness 的适配器；
2. 子 Harness：仍然提供自己的执行环境、权限、状态和反馈机制；
3. 子 Agent：才是某个具体 Purpose 在该环境中的 Runtime。

这样，DSH 获得的是跨 Host 的编排权，而不是越俎代庖地接管每个子 Host 的内部环境权。尤其不能因为有了 DSH 适配器，就绕过 Codex 的沙箱或 WorkBuddy 的企业权限。

所以，DSH 最适合的位置不是“另一个更强的 Agent”，而是 Purposes 的 Runtime Fabric：负责不同 Host 之间的实例化、委派、观察、调度和结果回收。

#### 2. 行动力比 Purpose 的符号展开更重要

更准确的表述是：AI 的可验证行动力，比 LLM 对 Purpose 的推演、分解和语言表述更重要。

因为 Purpose 本身通常不应由 LLM 自行发明。它首先来自用户、组织和现实任务；LLM 生成的是对 Purpose 的理解、子目标与计划、工具调用意图，以及对完成状态的解释。

如果 Purpose、行动验收和结果解释都由 LLM 自己生成，系统仍可能封闭在符号循环里。真正的语用接地，需要外部目的与环境结果共同约束它。

但这也不意味着行动力在规范上高于 Purpose：

> 没有行动力的 Purpose 只是愿望；没有 Purpose 约束的行动力只是失控的功率。

重要的不是“让 AI 做更多动作”，而是形成这种能力：

```text
在 Purpose 约束下改变环境
→ 读取真实反馈
→ 修正后续行动
→ 留下可验证的轨迹
→ 对行动后果保持可治理性
```

#### 3. 把行动轨迹显式补出来

若要进一步突出 Pragmatic Grounding，可以写成：

```text
Agentₚ = RunH,E(LLM, Purpose, State)
              ↓
Trajectory＝[(State₀, Action₀, Observation₀),
             (State₁, Action₁, Observation₁),
             …,
             Outcome]
```

其中：

- H：行动如何被执行；
- E：行动作用于什么真实环境；
- State：Agent 如何保持时间与身份连续；
- Observation：环境如何反驳或确认模型；
- Outcome：Purpose 是否真正达成；
- Trajectory：什么经验可以被验证、回放、归因和内化。

这样，Agent 的最终产物就不只是一个 Answer，而是 Outcome + Trajectory。DSH 作为 Meta-Host 最有价值的地方，也不只是返回“子 Agent 说了什么”，还应回收“子 Agent 做了什么、环境返回了什么、凭什么认为完成了”。

最终可以凝练为：

> LLM 提供行动策略的先验，Purpose 提供方向，Harness 提供现实作用面，State 提供持续主体性，而环境反馈赋予行动以真假。DSH 的价值，是让这些作用面本身也能被动态组装。
